# 0003 — One snapshot contract, shared by both paths and pinned by fixtures

**Status:** accepted, 2026-09-17.

## Context

Two integrations mean two ways to build the input of a decision: the plugin reads the
scheduler cache, the extender receives a serialised node list and queries the API. Left
alone, they drift — and a drift in the input looks exactly like a difference in the
integration, which is the thing we are trying to measure.

## Decision

Both paths build the same snapshot: pod identity and effective requests, per-node
allocatable, requested and measured resources, pod count, readiness, the age of each
measurement, and an explicit list of missing feature groups. Strategies are pure functions of
that snapshot.

The rules that could drift are pinned by shared fixtures, read by both test suites:

- `testdata/snapshots/*.json` — the chosen node and every normalised score, per strategy;
- `testdata/pod-requests.json` — effective pod requests, including sidecars and pod overhead;
- `testdata/quantities.json` — resource quantity parsing, generated by apimachinery itself;
- `testdata/quantisation.json` — score quantisation, case by case.

## Consequences

- A change to a strategy on one side only breaks one of the two suites immediately.
- A missing value is declared missing, never read as zero. A strategy that needs it fails and
  falls back explicitly, which is visible, instead of ranking on invented data.
- The effective request rule is not ours: the plugin calls upstream `PodRequests`, and the
  extender ports that algorithm. Hand-writing it produced two bugs before this decision —
  init containers ignored on one side, sidecars and pod overhead ignored on both.
- The fixtures are the contract. Adding a snapshot field means updating them.

## Revisit if

A path gains information the other cannot have at all. The honest response is then to record
the asymmetry in the snapshot's missing features and in the results, not to hide it by
lowering both paths to the poorer view.
